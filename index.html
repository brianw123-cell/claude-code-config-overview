The setup in one minute

The idea is simple: keep what Claude reads every session small, and load everything else only when it's relevant. That keeps each session focused and makes the rules easy to find and change.

A short always-on file

About 150 lines: who I am, how I like to communicate, and an index of everything else. Every session starts with it.

24 preference files, loaded on demand

Database setup, deploys, accessibility, privacy, security reviews, proposals. Each one loads only when its trigger comes up.

5 custom skills

Repeatable workflows: a client discovery audit, a standard app stack, quick prototypes, research with sources, and turning a call transcript into a summary, notes and a follow-up email.

4 spoken commands

I dictate most of my work, so commands fire on phrases like "wrap this up" (hand off to a fresh session) or "grill me" (get interviewed about a plan before building).

9 playbooks

Proof of concept, launch, integrations, agent design, client deliverables, discovery tracking. Each is a checklist I start from, not a template I fill in blind.

Project memory

Each project keeps short notes on facts that aren't in the code: decisions, client constraints, things I got wrong once and shouldn't again.

Guardrails: what Claude can do on its own

Most of the friction in AI work is permission prompts, and most of the risk is one action you can't take back. So I sort actions into three groups and write them down.

Pre-approvedReading project files, running tests and type checks, applying database changes to a development branch, committing and pushing to a feature branch. 47 narrow, named command patterns, never a blanket "allow all."
Always ask, no exceptionsPushing to the main branch, any change to a production database, force-pushing, deleting data or branches, anything that costs money, deploying to a real domain, and emailing or texting real customers.
NeverRunning with permission checks bypassed. Blanket access to file types that commonly hold secrets. Any agent that sends on its own: my production agent drafts, and a person approves every send.

Secrets get a second line of defense: a scan runs before every commit to my configuration, and client apps get a separate security review before launch.

Checks that run without me remembering

  • Session start: confirms my Google Drive access still works and that my scheduled automations still exist and ran recently. One of them had silently disappeared more than once, so now a missing one shows up in a single line.
  • Before a turn ends: if user-facing screens changed, the reply must include a numbered "test this" list I can follow click by click.
  • After a UI edit: a reminder to screenshot the changed page in a browser, so I see what users will see.
  • After a push: the deploy is followed through to "live" or "failed" and reported in the chat, instead of me refreshing a dashboard.
  • Before calling a build done: one type check across the whole change, with every finding fixed first.

Mistakes I turned into written rules

This is the part I'd most want a team to copy. When something goes wrong, the fix isn't "be more careful." It's a sentence in the setup, so the same mistake can't come back next week.

What happenedA client told me my emails felt "really AI driven" and were "way too much."
The rule nowEvery draft has a length level, a word count and a count of asks printed above it. The default is one point and one ask in 120 words. I have to ask for longer.
What happenedA tool I built and shipped was never actually used by the client.
The rule nowDescribe work as "built" unless someone is using it. Résumés, proposals and posts never claim adoption that didn't happen.
What happenedOn a data migration, a rehearsal showed that 2,331 moved members couldn't sign in.
The rule nowRehearse every cutover on a practice copy, as many times as it takes. That one was found weeks before launch, not on launch day.
What happenedA batch of documents went out with a file name as the page heading.
The rule nowA written note on how the tool works, plus a check of the first line of every PDF before it's handed over.

How I teach it

  • Start with their real work, not a feature tour. When I launched a booking app for a coaching business, I sat with the owner while he loaded his own sessions and gave him one rule to follow. Within two days he'd added 10 more.
  • Decide what not to automate. I check every workflow against four questions: is it rule-bound, where is human judgment really needed, what usable data exists, and what breaks downstream when a step is wrong. Most of what looks automatable fails the last two.
  • Write the policy before anyone builds. For clients new to AI, I draft a short use policy first: what data can go into which tools, and who approves what.
  • Hands-on sessions. I've hosted three build sessions at my house, where people bring a real task and leave with something working.
Why this matters for customers. Owners trust AI when they can see the guardrails, and teams get better at it when every mistake becomes a rule everyone can read. The same structure that keeps my own work safe is what I help clients set up: a small set of always-on rules, clear lines between "go ahead" and "ask first," and checks that run on their own.
